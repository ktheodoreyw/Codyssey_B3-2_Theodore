# 보너스 과제 2 — 커밋/PR 템플릿 커스터마이징

> **과제 요구**: 이전 미션 저장소의 커밋/PR 스타일을 분석해 "팀 컨벤션"을 정의하고(prefix 규칙, scope 사용 여부, PR 템플릿 섹션/톤/체크리스트), 도구에 컨벤션을 반영하는 방법을 1가지 이상 구현한다(설정 파일 / `--convention` 옵션 / 프롬프트 템플릿 교체).
> **제출(증빙)**: 컨벤션 문서(README 섹션) + 컨벤션 적용 전/후 생성 결과 비교 1회 이상

분석한 이전 미션 저장소는 [On-Premise-Sky/B2-2](https://github.com/On-Premise-Sky/B2-2) 입니다. 반영 방법은 제시된 세 가지(**설정 파일, `--convention` 옵션, 프롬프트 템플릿 교체**)를 모두 구현했고, 증빙으로 B2-2 에 실제로 있었던 커밋 2개와 PR 1개를 그 시점 상태로 재현해 **같은 diff** 로 적용 전/후를 생성하고, 팀원이 실제로 쓴 메시지와 나란히 비교했습니다.

## 3. 정의한 팀 컨벤션 (요약)

| 구분 | 규칙 |
|---|---|
| 커밋 제목 | `<type>: <무엇을 바꿨는지>` — type 은 `feat`/`fix`/`docs`/`refactor`/`chore`, **scope 없음**, 한글 50자 이내, 명사형 끝맺음, 마침표 없음 |
| 커밋 본문 | 필요할 때만, 불릿 없이 '~했습니다' 문장 1~3개, 바꾼 파일 경로 포함 |
| 금지 제목 | `update`, `fix`, `temp`, `wip`, `final`, `bug fix`, `edit file` |
| PR 제목 | 커밋과 같은 형식, 50자 이내 |
| PR 본문 | `## 관련 이슈`(`Closes #N`) → `## What (무엇을 바꿨나요)` 1~5개 → `## Why (왜 바꿨나요)` 1~3개 → `## How (어떻게 확인했나요)` 1~5개 → `## 체크리스트` 3개 |
| PR 문체 | What 은 '`파일 경로` 변경 내용', Why 는 존댓말 평서문, How 는 '~를 확인합니다'(실행하지 않은 결과를 '확인했습니다'로 단정하지 않음) |
| 체크리스트 | 커밋 메시지 컨벤션 준수 / 리뷰어 지정 / 리뷰 코멘트 응답 — 사람이 확인할 항목이라 빈 칸으로 생성 |
| 브랜치 | `^(feature\|fix\|docs)/[A-Za-z0-9_-]+-[a-z0-9][a-z0-9-]*$` — 어긋나면 `[경고]` |

전체 정의는 README 6장, 도구가 출력한 형태는 [raw/convention_b2-2.txt](raw/convention_b2-2.txt) 에 있습니다.

## 4. 도구에 반영한 방법

```bash
python main.py convention --convention b2-2        # 적용될 컨벤션 확인 (API 호출 없음)
python main.py commit --convention b2-2            # 프리셋으로 커밋 메시지
python main.py pr --convention b2-2 --issue 26     # PR 초안 + 'Closes #26'
python main.py commit --convention team.json       # 직접 만든 컨벤션 파일
python main.py commit                              # 대상 프로젝트의 .ai-gitgen.json 'convention' 자동 적용
python main.py commit --convention default         # 설정 파일이 있어도 기본 컨벤션으로
```

우선순위: `--convention` 옵션 → 대상 프로젝트 루트의 `.ai-gitgen.json` → 기본 컨벤션.

컨벤션은 **네 곳**에 반영됩니다. 프롬프트만 바꾸면 모델이 규칙을 어겨도 그대로 출력되기 때문입니다.

| 단계 | 코드 | 팀 컨벤션일 때 |
|---|---|---|
| 프롬프트 템플릿 교체 | `convention.system_prompt` | 팀 타입·설명, 제목 작성 요령, 금지 제목, 본문 문체, PR 섹션·문체, 팀의 실제 예시로 system 프롬프트를 새로 만듦 |
| 응답 스키마 | `convention.schema` | `type` enum 을 팀 타입 5종으로, scope 를 쓰지 않으면 `scope` 필드를 아예 빼고, PR 은 팀 섹션 key(`what`/`why`/`how`)로 |
| 조립 | `formatter.build_*_conv` | `format` 대로 제목, 본문은 문장으로, PR 은 템플릿 순서 + `Closes #N` + 체크리스트 |
| 검증 | `formatter.validate_*_conv` | 제목 형식·길이·금지 제목, 섹션 순서·항목 수, 이슈 번호, 체크리스트 개수, 브랜치 이름 |

- 잘못된 설정은 API 호출 전에 원인과 함께 거부합니다(종료 코드 2).
- **기본 컨벤션의 프롬프트·스키마·출력은 보너스 2 이전과 한 글자도 같습니다** — 기존 사용자는 영향이 없습니다(테스트로 확인).

## 5. 적용 전/후 생성 결과 비교

B2-2 에 실제로 있었던 변경 3건을 그 시점 상태로 재현해 **같은 diff** 로 적용 전(`--convention default`)과 적용 후(`--convention b2-2`)를 실제 API(`claude-opus-4-6`, temperature 0.2)로 생성하고, 팀원이 실제로 쓴 메시지와 함께 **팀 문서에서 뽑은 기준**으로 채점했습니다.

| 대상 | 고른 이유 | 팀원이 실제로 쓴 것 | 적용 전 | 적용 후 |
|---|---|---|---|---|
| C1 커밋 `docs: CONTRIBUTING에 히스토리 정리 기준 추가` | 커밋의 62%인 docs 타입, 본문 없는 짧은 커밋 | 4/4 | 4/5 | **5/5** |
| C2 커밋 `refactor: 팀원 데이터를 members.json으로 분리` | 파일 이동·삭제가 섞인 구조 변경, 본문까지 쓴 커밋 | 5/5 | 4/5 | **5/5** |
| P1 PR #27 (C2 와 같은 변경의 PR) | 템플릿 + 추가 섹션까지 쓴 PR | 6/6 | 1/6 | **5/6** |

채점 기준 — 커밋: `type: 설명` 형식(scope 없음), 팀 타입 5종, 제목 50자 이내, 한글·마침표 없음, (본문이 있으면) 불릿 없는 존댓말 문장. PR: 제목 형식, 제목 50자 이내, 템플릿 섹션 5개 순서, `Closes #번호`, 체크리스트 3개, Why 존댓말.

### 무엇이 달라졌나

| 항목 | 적용 전 (기본) | 적용 후 (B2-2 팀 컨벤션) |
|---|---|---|
| 커밋 본문 | `- members.json: 팀원 데이터를 …` ("파일명: 내용" 불릿) | `src/js/members.js에서 … 분리했습니다.` (불릿 없는 존댓말 문장 + 파일 경로, 팀원의 실제 습관) |
| PR 섹션 | `## Why` → `## What` → `## How to Test` | `## 관련 이슈` → `## What (무엇을 바꿨나요)` → `## Why (왜 바꿨나요)` → `## How (어떻게 확인했나요)` → `## 체크리스트` |
| 관련 이슈 | 없음 | `Closes #26` |
| Why / How 문체 | `… 분리가 필요`, `… 렌더링되는지 확인` (개조식) | `… 하기 위해서입니다`, `… 렌더링되는지 확인합니다` |
| 체크리스트 | 없음 | 팀 템플릿 3개 항목 (`- [ ]`, 사람이 직접 체크) |
| 비용 (3건 합계) | $0.0839 | $0.0852 — 프롬프트만 바꾸므로 거의 같음 |

### 남은 한계와 개선 과정

- 모델이 가장 자주 어긴 규칙은 **제목 길이**였습니다. 리뷰 반영 중 실행한 2회차에서는 C2·P1 제목이 56자·55자로 넘쳤습니다.
- 그래서 '제목 전체 50자 이내'만 알려 주던 프롬프트를, 형식 머리말을 뺀 **subject 한도를 타입별 숫자로** 알려 주도록 고쳤습니다(예: `refactor` 는 50 − `refactor: `(10자) = 40자).
- 최종 실행에서 C2 는 35자로 통과했지만 P1 PR 제목은 두 가지 변경을 한 제목에 담아 53자로 여전히 넘었습니다. 도구는 이를 `[경고] PR 제목 53자 (팀 기준 50자 이내)` 로 알려 줍니다([raw/P1_after.txt](raw/P1_after.txt)). 자르면 뜻이 깨지므로 자르지 않고 사람이 다듬게 합니다.
- 생성 결과는 실행마다 조금씩 다릅니다. 위 표는 최종 1회 실행 결과를 그대로 옮긴 것이고, 점수를 높이려고 결과를 골라 쓰지 않았습니다.

## 6. 재현 방법

```bash
# 실제 API 로 다시 생성 (6회 호출, .env 의 API Key 사용)
python scripts/bonus2_evidence.py

# API 없이 분석 + dry-run 만 (스크립트 점검용, 비용 0, 결과는 임시 폴더에 — 이 폴더를 덮어쓰지 않음)
python scripts/bonus2_evidence.py --skip-api

# API 재호출 없이 기존 raw/ 결과로 보고서만 다시 생성
python scripts/bonus2_evidence.py --reuse-raw
```

스크립트는 B2-2 를 임시 폴더에 clone 해서 ① 커밋·PR 통계를 다시 계산하고 ② 비교 대상 커밋의 부모로 이동해 그 커밋의 변경을 스테이징하거나(커밋), 머지 직전 브랜치를 만들어(PR) 같은 diff 로 `--convention default` 와 `--convention b2-2` 를 실행합니다. 채점은 도구의 검증 함수가 아니라 팀 문서에서 뽑은 기준으로 스크립트가 따로 합니다.

- **격리**: 사용자의 전역 git 설정이 결과에 영향을 주지 않게 하고, 임시 복사본이 자기 `.git` 을 쓰는지 확인한 뒤에만 `reset --hard` 같은 명령을 실행합니다(`--repo` 는 독립 clone 만 받음 — worktree 를 복사하면 원래 저장소가 바뀌기 때문).
- **실패해도 기존 증빙 보존**: 결과를 임시 폴더에서 모두 만든 뒤, 끝까지 성공했을 때만 `raw/` 와 `EVIDENCE.md` 를 바꿉니다.
- **지어낸 점수 없음**: GitHub 에서 실제 PR 을 못 불러오거나 생성 결과를 못 찾으면 실패하고, dry-run 결과는 채점하지 않고 `–` 로 표시합니다.
- 생성된 문서에 개인 PC 경로가 남으면 실패합니다. 끝나면 임시 폴더를 지웁니다.
- 모델 출력은 매번 조금씩 다를 수 있습니다(temperature 0.2).

- 컨벤션 불러오기: 프리셋, 파일 경로, 프로젝트 `.ai-gitgen.json` 자동 적용, `--convention default` 우선, 없는 이름, 섹션 밖 항목(섹션이 있어도), 틀린 섹션 이름

- **하위 호환**: 기본 컨벤션의 프롬프트·스키마가 보너스 2 이전 코드의 sha256 과 같은지, 조립·검증 결과가 이전 코드의 결과와 같은지(이전 값을 테스트에 고정)
- 팀 프롬프트·스키마(타입 enum, scope 제거, 섹션 key, 프롬프트와 스키마의 필드 일치)

- CLI: 프리셋 적용, `pr --issue` + 브랜치 이름 OK/경고, 설정 파일 자동 적용과 `default` 우선, 잘못된 설정 종료 코드 2, `--issue` 경고, `convention` 명령, dry-run 의 팀 응답 스키마 표시
